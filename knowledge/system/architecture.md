# Архитектура системы

## Из чего состоит

```
Telegram-группа с топиками
        │  (поллинг)
   ┌────▼─────┐
   │  bridge  │  tg_bridge.py — оркестратор
   └────┬─────┘
        │ роутит по (chat_id, topic_id)
   ┌────┼────────┬─────────┐
 Ассистент   Сисадмин   Скрайбер   ← агенты (каждый = папка + CLAUDE.md)
        │
   runner (claude/codex/deepseek/gemini CLI или API)
```

## Мост (bridge/)

Один процесс `tg_bridge.py`. Что делает:
- **Поллит** Telegram (getUpdates) по каждому уникальному bot token.
- **Роутит** сообщение по `(chat_id, topic_id)` → находит агента в `agents.toml`.
- **Запускает** runner агента (CLI-сессия), стримит ответ обратно в топик.
- **Очередь** на агента: пока агент BUSY, сообщения копятся и склеиваются.
- **State machine**: помнит состояние каждого агента между сообщениями.
- **Делегация**: парсит теги `[DELEGATE:X]` → передаёт задачу агенту X.
- **Maintenance loop** (фон): hot-reload конфига, daily reset, keep-alive, обработка cron-очереди.

## Агент

Папка `agents/<name>/`:
- `CLAUDE.md` — роль и инструкции (читается при каждом старте сессии)
- `context.md` — память между сессиями
- `journal.md` — уроки/история
- `AGENTS.md`, `GEMINI.md` — симлинки на CLAUDE.md (для Codex/Gemini)

Агент = промпт + рабочая папка + runner. Мост держит для него сессию.

## Routing: один бот — много агентов

В `agents.toml` все агенты могут иметь один `bot_token_env = "BOT_TOKEN"`. Мост:
1. Группирует агентов по токену.
2. На каждый уникальный токен — один поллер.
3. Поллер ловит сообщения из всех топиков → по topic_id определяет агента.

Хочешь отдельного бота с аватаркой — заведи второй токен в @BotFather, укажи другой `bot_token_env`.

## Конфигурация

- `bridge/agents.toml` — агенты (hot-reload каждые 60 сек, рестарт не нужен).
- `bridge/.env` — секреты (токены, API-ключи). Правка → нужен рестарт.
- `bridge/settings.json` — permissions (что агентам запрещено).

## Где что лежит (от AIOS_ROOT)
